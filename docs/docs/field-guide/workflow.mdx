# Field Guide: Workflow Agents

Positioning, objection handling, and demo scripts for account teams.

## Common Objections & Responses

<div className="fancy-table">

| Objection                                    | Response                                                                                                                                                          |
|----------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| "Why not just Step Functions?"               | Step Functions handle deterministic workflows. Agents handle ambiguous decisions. Use both: Step Functions for orchestration, AgentCore for reasoning steps.       |
| "What if the agent makes a wrong decision?"  | Cedar policies bound what it *can* do. Online evaluations catch regressions in real-time. DLQ + audit trail enable replay.                                        |
| "What about latency for event processing?"   | End-to-end (trigger to action) is typically seconds to low tens of seconds. A human reviewing the same event takes minutes to hours.                              |
| "How does this compare to Bedrock Agents?"   | AgentCore adds Runtime isolation (microVM), Policy Engine (Cedar bounded autonomy), online evaluations, and MCP Gateway on top of Bedrock's model capabilities.   |
| "What about cost for high-volume events?"    | Scale-to-zero + model routing (Haiku for simple triage, Sonnet for complex reasoning) means you pay only for reasoning that matters.                              |
| "Is it production-ready?"                    | Cox Automotive, Iberdrola, Rede Mater Dei, and Thomson Reuters are running workflow agents in production today.                                                    |

</div>

## What to Demo (5-Minute Path)

**Prerequisite (before the meeting):** Deploy the [IT Incident Response sample](https://github.com/awslabs/agentcore-samples/tree/main/02-use-cases/02-workflow-automation-agents). This provisions the full reference architecture: EventBridge custom bus, trigger Lambda (+ DLQ), Runtime agent, Gateway tools (`restart_service`, `get_metrics`), and Cedar policy. Confirm observability is enabled.

1. **Publish an event**: Fire a test event at the sample's EventBridge bus:

   ```bash
   aws events put-events --entries '[{
     "EventBusName": "incident-bus",
     "Source": "demo.incidents",
     "DetailType": "IncidentOpened",
     "Detail": "{\"entity_id\":\"INC-12345\",\"event_type\":\"service_down\",\"priority\":\"HIGH\",\"context\":{\"service\":\"checkout-api\"}}"
   }]'
   ```

2. **Watch the agent reason**: Open CloudWatch traces, show the agent receiving the event, calling tools, deciding action.
3. **Show the Cedar policy**: Demonstrate that the agent is bounded: it can restart services but cannot delete resources.
4. **Show the evaluation**: Point to online eval metrics proving the agent's decisions are correct.
5. **Point to production**: `agentcore deploy` is one command. No Kubernetes, no container orchestration, no infrastructure management.

**Key outcome message:** "This agent processes events autonomously within defined boundaries. It reasons about ambiguous situations, takes action, and we can prove its decisions are correct."
