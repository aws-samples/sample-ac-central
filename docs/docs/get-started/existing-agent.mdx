# Adopt AgentCore with an Existing Agent

If your agent already works, you do not need to rewrite it to use AgentCore. This page walks through incremental adoption: deploy your existing code to AgentCore Runtime first, then layer in the platform services you need.

Each step is self-contained. Go as far as your requirements warrant. You do not need to complete all six steps to get value from AgentCore.

:::info Prerequisites
Complete the [Preflight Checklist](/docs/get-started/preflight) before starting. Pay particular attention to the runtime execution role; your existing agent likely has permissions scoped to its current host, and those need to carry over to AgentCore Runtime.
:::

---

## Step 1: Deploy your existing agent to AgentCore Runtime

AgentCore Runtime accepts your existing agent code with minimal changes. It runs in a microVM-isolated container with scale-to-zero and OpenTelemetry tracing built in.

**What to do:**

1. Install the `bedrock-agentcore` SDK into your project: `uv add bedrock-agentcore` (or `pip install bedrock-agentcore`).
2. Wrap your agent's entry point with `BedrockAgentCoreApp`. The key change is replacing however your agent currently receives requests with the `@app.entrypoint` decorator. For most frameworks, this is a small wrapper around the framework's own invocation pattern.
3. Configure the deployment in `agentcore/agentcore.json` (scaffold with `agentcore create --skip-install` and edit, or write from the reference in the [CLI quickstart](/docs/get-started/quickstart)).
4. Run `agentcore dev` locally to verify the wrapper works before deploying.
5. Run `agentcore deploy` to push to AgentCore Runtime.

**Framework-specific notes:**
- **Strands**: `BedrockAgentCoreApp` is designed for Strands and the integration is direct.
- **LangGraph / LangChain**: wrap your graph's `invoke` or `stream` call inside `@app.entrypoint`.
- **CrewAI**: wrap your `Crew.kickoff()` call inside `@app.entrypoint`.
- **Custom frameworks**: any Python callable can be wrapped; the entrypoint receives a `payload` dict and a `context` object.

For the full deployment reference, see the [AgentCore Developer Guide](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/).

**Next:** Confirm your agent responds correctly via `agentcore invoke` before moving to Step 2.

## Step 2: Enable Observability

Once your agent is on Runtime, turn on tracing. This gives you distributed traces for every invocation: which tools were called, how long each step took, and where errors occurred.

**What to do:**

Add the observability configuration to your `agentcore.json`:

```json
{
  "observability": {
    "enabled": true,
    "destination": "CloudWatch"
  }
}
```

Then redeploy with `agentcore deploy`.

Traces appear in CloudWatch under your agent's log group. If you already use an OTLP-compatible backend, you can configure an OTLP export endpoint instead of CloudWatch.

**Why do this early:** Observability is the fastest way to understand how your existing agent behaves in the new environment. Issues that were invisible on your previous host often surface immediately in traces.

For the full reference, see the [Observability & Evaluations overview](/docs/agent-platform/observability-evals) and the [AgentCore Developer Guide](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/).

## Step 3: Add Memory (if needed)

If your existing agent manages session state itself (passing conversation history in each request, writing to a database), you can offload that to AgentCore Memory.

**What to add:**

AgentCore Memory provides two scopes:
- **Session memory**: short-term context within a session, up to 8 hours by default
- **User memory**: long-term facts and preferences persisted across sessions, scoped per user ID

Add a memory configuration to `agentcore.json` via `agentcore add memory`, then update your agent code to read from and write to the Memory API instead of your existing state management.

**When to skip:** If your agent is stateless or manages state externally and that approach is working, skip this step. Adding Memory is most valuable when you need cross-session persistence or want to reduce the context you pass on every call.

For the full reference, see the [Add Memory tutorial](/docs/tutorials/add-memory) and the [AgentCore Developer Guide](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/).

## Step 4: Add Gateway tools

AgentCore Gateway federates tool access via the Model Context Protocol (MCP). If your existing agent calls external APIs, those calls can move behind Gateway to get centralized auth, logging, and policy enforcement.

**What to add:**

1. Define your existing tool endpoints as Gateway configurations in `agentcore.json` via `agentcore add gateway`.
2. Gateway targets can be Lambda functions, HTTP endpoints, or existing MCP servers.
3. Inbound requests to the gateway are authenticated with JWT; your tools do not need to handle auth directly.
4. Add Cedar policies to restrict which tools your agent can call and under what conditions (see the [Policy Engine reference](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/)).

**When to skip:** If your agent's tools are simple wrappers around AWS SDKs and do not need centralized auth or policy, you can leave them as inline tool calls and add Gateway later when you need multi-agent tool sharing or stricter policy enforcement.

For the full reference, see the [AgentCore Developer Guide](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/).

## Step 5: Add Identity

If your agent acts on behalf of users and needs to call tools with user-scoped permissions, AgentCore Identity handles OAuth/OIDC token brokering. Your agent requests a token for a specific user; Identity brokers the exchange with your identity provider. The agent never sees client secrets.

**What to add:**

1. Configure your OAuth provider in the AgentCore console or via the Identity API.
2. Add the identity configuration to `agentcore.json`.
3. Update your agent code to request a user-scoped token from the Identity service and forward it to downstream tool calls.

**When to skip:** If your agent runs on behalf of a service account (not individual users) and does not need per-user authorization, skip Identity for now.

For the full reference, see the [Security and Identity](/docs/operate/security-and-identity) page and the [AgentCore Developer Guide](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/).

## Step 6: Prepare for production

Before routing real traffic to your adopted agent, work through the production readiness checklist. The items most relevant to an existing agent adoption are:

- IAM least-privilege: does the runtime execution role grant only what this agent actually needs?
- Tenant isolation: if the agent serves multiple users or teams, are Memory namespaces and tool access scoped per tenant?
- Guardrails and policy: have you applied content filters and Cedar policies appropriate to the agent's risk level?
- Evaluations: do you have a baseline dataset and evaluation pipeline before you start receiving real traffic?
- Rollback: can you redeploy the previous version quickly if something regresses?
