# Quick Start: Conversational Agent on Harness

Use AgentCore Harness when you want a managed conversational agent loop driven by configuration, not code.

:::caution Prototype, not production
The Harness getting-started tutorial creates a prototype, not a production-ready system. Before routing real users or data to it, work through the [Production Readiness checklist](/docs/operate/production-readiness).
:::

---

## Create, deploy, and invoke in three commands

```bash
# Create a harness project
agentcore create --name mychatagent --model-provider bedrock

# Add memory for multi-turn conversation continuity
agentcore add memory --name chatmemory --strategies SEMANTIC,SUMMARIZATION
```

After scaffolding, edit `app/mychatagent/system-prompt.md` with a conversational system prompt:

```markdown
You are a helpful assistant that answers questions clearly and concisely.

## Guidelines
- Ask clarifying questions when a request is ambiguous.
- When you don't know something, say so — don't guess.
- Keep responses focused on the user's question.
- If a task requires multiple steps, walk the user through them one at a time.
- Never share information about other users or internal systems.
```

Then run the dev server to test:

```bash
# Deploys the harness and opens a browser test page for interactive chat
agentcore dev
```

`agentcore dev` synthesizes and deploys the harness automatically, then opens a test page where you can chat with the agent, inspect traces, and adjust settings. Use `--no-browser` for a terminal-based TUI instead.

Alternatively, invoke directly from the CLI:

```bash
agentcore invoke --harness mychatagent \
  --session-id "$(uuidgen)" \
  --actor-id alice \
  "What can you help me with?"
```

`--actor-id` scopes memory per user — each actor gets isolated short-term and long-term recall. The name must be alphanumeric only (no hyphens or special characters). For the full interactive wizard and configuration options, see the [Harness Getting Started tutorial](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-get-started.html).

## When Harness suffices vs. when you need a full-stack sample

| Choose Harness when | Choose the conversational sample when |
|---|---|
| Declarative config (model, prompt, tools, memory) covers your requirements | You need custom orchestration logic or a framework other than Strands |
| You want per-user memory without writing session-manager code | You need streaming responses with custom middleware or client integration |
| Your tools are available as remote MCP servers, gateways, or inline functions | Your tools require local Python functions or complex dependency graphs |
| You want the fastest path from idea to working prototype | You need full control over identity extraction, session lifecycle, or error handling |

Harness is a managed version of the same agent loop you would write with the [Runtime path](/docs/workloads/conversational/quickstart). It is powered by Strands and runs inside Runtime. If your requirements outgrow declarative configuration, the Runtime path gives you full code-level control.

## Sandbox scoping and production boundaries

Harness tutorials create resources in a **sandbox scope** — meaning the agent can converse but has no access to external systems or verified user identities by default:

- **Default tools included** — the harness is created with `shell` and `file_operations` tools available. The agent can execute commands and interact with the filesystem within its sandboxed microVM. Additional tools (MCP servers, Gateway targets, browser, code interpreter) are added via `agentcore add tool` and require corresponding permissions on the [execution role](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html#harness-execution-role-policy).
- **Actor IDs are caller-supplied** — `--actor-id` is an opaque identifier that AgentCore does not verify against an authenticated user. In production, derive actor IDs from verified JWT claims via [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/identity.html).
- **Memory is namespaced by actor** — sharing one actor ID across users would let them read each other's context. See [Per-user memory scoping with actor ID](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-memory.html).
- **No inbound authorization** — by default, anyone with IAM `InvokeHarness` permission can invoke. Production harnesses should add [inbound OAuth](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html) or scope IAM policies to specific principals.

For the full security model — trust boundaries, execution role policies, tool permissions, network configuration, and gateway policy integration — see [Harness security and access controls](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-security.html). The [Runtime security best practices](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-security-best-practices.html) apply equally since harness runs inside Runtime.

When moving toward production, complete the <Link to="/docs/operate/production-readiness">Production Readiness checklist</Link>.
