# Quick Start: Conversational Agent

Deploy a working chat agent with memory in under 10 minutes.

| | |
|---|---|
| **Who this is for** | Developers building conversational or customer-facing agents |
| **Time** | ~10 minutes |
| **What you'll build** | A chat agent with account lookup and optional cross-session memory |
| **Safety level** | Creates real AWS resources; uses simulated account data; no external write actions |

## 5 Steps to Deploy

<div className="fancy-table fancy-table--auto-first">

| Step | Action          | Command                                             |
|------|-----------------|-----------------------------------------------------|
| 1    | Install CLI     | `npm install -g @aws/agentcore@0.24.1`              |
| 2    | Create project  | `agentcore create` with the options below           |
| 3    | Install deps    | `cd app/ChatAgent && uv venv && uv sync && cd ../..` |

### Create the project and agent

Run this command from the directory where you want the project folder to be created. The explicit names ensure that the generated paths match the rest of this quickstart: `chatagent/app/ChatAgent/main.py` and `chatagent/app/ChatAgent/pyproject.toml`.

```bash
npm install -g @aws/agentcore@0.24.1
agentcore --version
agentcore create \
  --name ChatAgent \
  --project-name chatagent \
  --framework Strands \
  --model-provider Bedrock \
  --memory longAndShortTerm \
  --build CodeZip \
  --language Python \
  --protocol HTTP \
  --network-mode PUBLIC
cd chatagent
```

The `--name ChatAgent` value controls the generated agent directory under `app/`, while `--project-name chatagent` controls the project directory. The project name must start with a letter, contain only alphanumeric characters, and be no more than 23 characters long. The `longAndShortTerm` memory option matches the `ChatAgentMemory` configuration shown below.

See the [official AgentCore CLI project creation guide](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/agentcore-get-started-cli.html) for the interactive wizard and current command options.

### Install Python dependencies

The generated project already declares `strands-agents` and `bedrock-agentcore` as dependencies in `app/ChatAgent/pyproject.toml`. Create the environment and install them:

```bash
cd app/ChatAgent
uv venv && uv sync
cd ../..
```

## Complete Working Example

A conversational agent with memory that remembers user preferences across sessions. Copy this into `app/ChatAgent/main.py`:

```python
"""Conversational agent with memory and a lookup tool."""

import logging
import os

from strands import Agent, tool

from bedrock_agentcore.memory.integrations.strands.config import AgentCoreMemoryConfig
from bedrock_agentcore.memory.integrations.strands.session_manager import (
    AgentCoreMemorySessionManager,
)
from bedrock_agentcore.runtime import BedrockAgentCoreApp

log = logging.getLogger(__name__)
app = BedrockAgentCoreApp()


@tool
def lookup_account(account_id: str) -> dict:
    """Look up account details by ID.

    Args:
        account_id: The customer account identifier.

    Returns:
        Account information including name, plan, and status.
    """
    # Replace with real API call in production
    accounts = {
        "ACC-001": {"name": "Acme Corp", "plan": "Enterprise", "status": "active"},
        "ACC-002": {"name": "Startup Inc", "plan": "Growth", "status": "active"},
    }
    account = accounts.get(account_id)
    if not account:
        return {"error": f"Account {account_id} not found"}
    return {
        "status": "success",
        "content": [{"text": str(account)}],
    }


SYSTEM_PROMPT = """You are a helpful customer support assistant.
You can look up account information when users provide an account ID.
Be concise, friendly, and accurate. If you don't know something, say so."""


RUNTIME_ACTOR_ID_HEADER = "x-amzn-bedrock-agentcore-runtime-custom-actor-id"


def get_actor_id(context) -> str | None:
    """Get the actor ID from an allowlisted Runtime header or local config."""
    headers = getattr(context, "request_headers", None) or {}
    normalized_headers = {str(name).lower(): value for name, value in headers.items()}
    return normalized_headers.get(RUNTIME_ACTOR_ID_HEADER) or os.environ.get(
        "AGENTCORE_ACTOR_ID"
    )


@app.entrypoint
def invoke(payload, context):
    """Agent entrypoint - called by AgentCore Runtime on each request."""
    prompt = payload.get("prompt", "Hello!")

    # RequestContext provides session_id and allowlisted request_headers. Deployed
    # callers pass a stable actor ID in the custom header; local dev falls back
    # to the explicitly configured actor ID. Validate identity in production.
    session_id = context.session_id or os.environ.get("AGENTCORE_SESSION_ID")
    actor_id = get_actor_id(context)

    session_manager = None
    try:
        memory_id = os.environ.get("BEDROCK_AGENTCORE_MEMORY_ID") or os.environ.get(
            "MEMORY_CHATAGENTMEMORY_ID"
        )
        region = os.environ.get("AWS_REGION")
        if memory_id and region and session_id and actor_id:
            memory_config = AgentCoreMemoryConfig(
                memory_id=memory_id,
                session_id=session_id,
                actor_id=actor_id,
            )
            session_manager = AgentCoreMemorySessionManager(
                memory_config,
                region_name=region,
            )
        elif memory_id:
            log.warning(
                "Memory configured but identity is incomplete; pass "
                "X-Amzn-Bedrock-AgentCore-Runtime-Custom-Actor-Id when deployed "
                "or set AGENTCORE_ACTOR_ID and AGENTCORE_SESSION_ID for local dev"
            )
    except Exception:
        log.exception("Memory unavailable (running without it)")

    agent = Agent(
        model="global.anthropic.claude-sonnet-4-5-20250929-v1:0",
        system_prompt=SYSTEM_PROMPT,
        tools=[lookup_account],
        session_manager=session_manager,
    )

    result = agent(prompt)
    return {"response": result.message}


if __name__ == "__main__":
    app.run()
```

:::warning Identity in multi-user deployments
`RequestContext` exposes `session_id` and the allowlisted `request_headers`. The deployed test passes the Memory actor ID in the `X-Amzn-Bedrock-AgentCore-Runtime-Custom-Actor-Id` header, which must be listed in the runtime's `requestHeaderAllowlist` (see Configuration below). The CLI's `--user-id` option maps to `runtimeUserId`, which AgentCore Identity consumes for OAuth token flows — it is never forwarded to your agent code. The quickstart falls back to `AGENTCORE_ACTOR_ID` for local testing. Because the header value is caller-supplied, validate it against a verified identity source before production use — for example, validated JWT claims from [AgentCore Identity](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/) or your own auth layer. Never use one shared actor ID for multiple users; Memory is namespaced by `actor_id`, so a shared value would allow users to share memory.
:::

:::warning Runtime version emitted by the CLI

## Test It

Run these commands from the generated `chatagent/` project directory. The `--no-browser` option opens an interactive terminal session; you do not need a second terminal to send prompts.

### Test the agent locally without deployed memory

```bash
agentcore dev --no-browser
```

Wait for the `>` prompt, then enter each message and press **Enter**:

```text
Look up account ACC-001
What plan are they on?
```

The first prompt should return the simulated Acme Corp account details. Before `ChatAgentMemory` is deployed, the local server displays this warning:

```text
AgentCore memory must be deployed before it can be used.
```

The second prompt can therefore ask for the account ID again instead of remembering `ACC-001`. This local test verifies the agent and lookup tool, but it does not verify memory persistence.

:::warning Memory requires deployment
The quickstart configures `ChatAgentMemory`, but `agentcore dev` does not create that AWS resource. Do not expect memory-backed multi-turn behavior until you deploy the project and restart the dev server.
:::

### Test with deployed memory

Deploy the project from the `chatagent/` directory. Deployment can take up to **8 minutes** while AgentCore provisions and updates the Runtime infrastructure:

```bash
agentcore deploy
```

After deployment, retrieve the deployed Memory ID and target region:

```bash
agentcore status --type memory --json
```

In the JSON output, use the value at `deployedState.targets.<target>.resources.memories.ChatAgentMemory.memoryId`. Use the Memory **ID**, not the ARN in `resources[].identifier`. Then create or edit `agentcore/.env.local` — this is the environment file loaded by the AgentCore CLI:

```dotenv
BEDROCK_AGENTCORE_MEMORY_ID=<memory-id-from-agentcore-status>
AWS_REGION=<targetRegion-from-agentcore-status>
AGENTCORE_ACTOR_ID=local-developer
AGENTCORE_SESSION_ID=chat-demo-session
```

`BEDROCK_AGENTCORE_MEMORY_ID` is the local-development variable. For the deployed CodeZip Runtime, the AgentCore CLI injects the generated resource variable `MEMORY_CHATAGENTMEMORY_ID`; the example code reads either variable. `AGENTCORE_ACTOR_ID` identifies the local test user and `AGENTCORE_SESSION_ID` keeps both interactive prompts in one Memory session. Use a new session ID when you want to start a fresh conversation. For production traffic, replace these local values with IDs from a verified identity source rather than sharing them across users. Keep `.env.local` out of source control and restart the local dev server after changing it:

```bash
agentcore dev --no-browser
```

Deployment creates AWS resources and may incur charges. In the interactive terminal, enter:

```text
Look up account ACC-001
What plan are they on?
```

With the deployed Memory ID configured, the second prompt should be able to use the account ID from the first prompt and return the Enterprise plan. Keep both prompts in the same interactive session when testing multi-turn memory.

If you want to test the deployed Runtime directly instead, local `.env.local` configuration is not required. Redeploy the project after changing the agent code, then generate one Runtime session ID and reuse it for both calls. AgentCore requires a Runtime session ID with at least 33 characters; a UUID satisfies this requirement:

```bash
SESSION_ID="$(uuidgen)"
agentcore invoke --session-id "$SESSION_ID" \
  -H "X-Amzn-Bedrock-AgentCore-Runtime-Custom-Actor-Id: demo-user" \
  "Look up account ACC-001"
agentcore invoke --session-id "$SESSION_ID" \
  -H "X-Amzn-Bedrock-AgentCore-Runtime-Custom-Actor-Id: demo-user" \
  "What plan are they on?"
```

The `-H` option passes the custom actor header to the deployed Runtime; the example code reads it from `context.request_headers` to scope Memory. The header only reaches your code because it is listed in the runtime's `requestHeaderAllowlist`. Do not use `--user-id` for this purpose — it maps to `runtimeUserId`, which AgentCore Identity consumes and never forwards to agent code. Run both invocations consecutively in the same shell: the second command cannot recover the first turn if the first command was not run with this exact `SESSION_ID`. Use a different session ID for a new conversation and a different actor ID for a different user.

## Placeholders in This File

The example code uses these values that you must supply for your own deployment:

- `ACC-001`, `ACC-002` — sample account IDs for the simulated lookup; replace with real data sources in your implementation
- `BEDROCK_AGENTCORE_MEMORY_ID` — local `agentcore dev` variable; set this to the deployed `ChatAgentMemory` `memoryId` returned by `agentcore status --type memory --json`
- `MEMORY_CHATAGENTMEMORY_ID` — injected automatically into the deployed CodeZip Runtime by the AgentCore CLI for the `ChatAgentMemory` resource
- `AWS_REGION` — set this to the `targetRegion` returned by `agentcore status --type memory --json`; it must match the Memory's deployment region
- `AGENTCORE_ACTOR_ID` — stable local test-user ID; use verified per-user identity values in production
- `AGENTCORE_SESSION_ID` — stable local session ID for multi-turn testing; use a new value to start a fresh conversation
- `X-Amzn-Bedrock-AgentCore-Runtime-Custom-Actor-Id` — allowlisted custom header carrying the deployed Memory actor ID; passed with `-H` on `agentcore invoke` and read from `context.request_headers`
- `demo-user` — example actor ID for the deployed test; each real user needs a unique, verified value

## What This Creates and What It Costs

Deploying this quickstart creates the following AWS resources:

| Resource | Notes |
|---|---|
| AgentCore Runtime | Hosts your agent code in MicroVM isolation |
| AgentCore Memory | Stores conversation facts and summaries (if configured) |
| IAM execution role | Least-privilege role for the Runtime |
| CloudWatch log groups | Receives runtime and invocation logs |

**Main cost drivers:**
- **Model inference tokens** — every invocation calls Claude Sonnet 4.5 on Amazon Bedrock; you pay per input/output token
- **Memory storage and retrieval** — AgentCore Memory charges for events stored and semantic retrievals performed
- **Runtime execution seconds** — billed per second of agent execution; scale-to-zero means no charges between invocations
- **Log ingestion** — CloudWatch charges per GB ingested and stored

**Scale-to-zero does not mean zero cost.** Memory records and CloudWatch log retention continue to accrue charges even with no active traffic. Remove resources when you're done experimenting.

## Cleanup

When you are done with this prototype, remove the resources managed by the project configuration. `agentcore remove all` resets the local AgentCore resource configuration, and the following `agentcore deploy` applies the empty state to AWS:

```bash
# From your agent project directory; review the confirmation prompt before continuing
agentcore remove all
agentcore deploy
```

Verify resources are gone:

```bash
agentcore status
# Expected: no runtimes or memory resources listed
```

Some resources may persist after cleanup:

- **AgentCore Memory** — memory records are retained by default until their `eventExpiryDuration` elapses; delete the memory resource explicitly if needed
- **CloudWatch log groups** — retained by default; delete manually to stop log storage charges

If cleanup reports errors, see [Cleanup Failures](/docs/reference/troubleshooting#cleanup-failures).
