### Managed Isolation vs. Generic Subprocess Execution

Coding agents that execute code must choose between two fundamentally different isolation models. Conflating them creates security risks:

| | Code Interpreter (Managed Isolation) | subprocess.run() (Generic Subprocess) |
|---|---|---|
| **Execution environment** | Fully managed, isolated sandbox provided by AgentCore | Same container, same filesystem, same network as the agent |
| **Filesystem access** | Isolated — cannot read or write the agent's files | Shared — can read/write anything the agent process can |
| **Network access** | Restricted by sandbox policy | Same network as the agent (VPC, internet access, internal APIs) |
| **Credential exposure** | None — sandbox has no access to agent credentials | Full — inherits the agent's IAM role and environment variables |
| **Use case** | Untrusted or user-supplied code, agent-generated code that needs validation | Trusted, deterministic operations where isolation is unnecessary (e.g., running a known linter) |
| **Blast radius** | Contained to the sandbox session | Entire agent container and anything it can reach |

:::danger Choose the right model for your risk level
- **Use Code Interpreter** when executing agent-generated code, user-supplied code, or any code whose behavior you cannot fully predict. This is the default recommendation.
- **Use subprocess.run()** only for trusted, deterministic commands (running a known test suite, formatting code with a pinned tool version) where you control every input and the failure mode is acceptable.
- **Never use subprocess.run() as a "sandbox"** — restricted `PATH` or `env` variables do not provide isolation. A malicious or buggy script still shares the agent's filesystem, network, and credentials.
:::

### Repository and Data Boundaries

Coding agents often need access to source code repositories and project data. Define clear boundaries:

- **Repository access scope** — Grant read access only to the specific repositories the agent needs. Use fine-grained tokens (GitHub App installation tokens, GitLab project access tokens) scoped to individual repositories, not organization-wide personal access tokens.
- **Data classification** — Determine whether the code the agent processes contains secrets, PII, or proprietary logic. If it does, Code Interpreter's isolated sandbox prevents that data from leaking through agent-side file access or network calls.
- **Output boundaries** — Define where agent-generated code can be written. Restrict to specific branches, draft PRs requiring human review, or ephemeral preview environments. Never auto-merge agent output to primary branches without approval.
- **Input validation** — Validate file paths, repository references, and code payloads before passing them to execution tools. Reject path traversal patterns, excessively large files, and unexpected file types.

### Approval Controls

Before a coding agent's output reaches production systems, enforce approval gates:

- **Human-in-the-loop for write actions** — Agent-generated code should create draft PRs or staged changes that require human review before merging.
- **Policy-gated execution** — Use Cedar policies to restrict which code execution tools can be invoked, by which principals, and under what conditions (repository scope, file type restrictions, time windows).
- **Execution budget limits** — Set `maxIterations` and `timeoutSeconds` to bound how many execution cycles the agent can attempt. This prevents runaway validation loops from consuming resources.
- **Audit trail** — Log every code execution request, its inputs, outputs, and the policy decision that allowed it. This is required for compliance and incident investigation.

### Resource and Cost Awareness

| Cost Driver | What Generates It | How to Manage |
|---|---|---|
| Model inference tokens | Plan and Generate phases call the LLM; multi-turn validation loops multiply token usage | Choose model size for your task; set iteration limits |
| Code Interpreter sessions | Each execution creates an isolated sandbox session | Set session timeouts; reuse sessions within a single invocation when possible |
| Runtime execution seconds | Agent processing time billed per second | Scale-to-zero; bound validation loops with `maxIterations` |
| Log ingestion | CloudWatch charges per GB for execution logs and outputs | Set retention policies; filter verbose execution output |

Scale-to-zero does not mean zero cost. Code Interpreter session storage and CloudWatch log retention continue to accrue charges even with no active traffic. Remove prototype resources when done experimenting.
