## Complete Working Example

An event-driven incident response agent that follows the 5-step pattern: Trigger → Enrich → Reason → Act → Emit. Copy this into `app/IncidentAgent/main.py`:

```python
"""Event-driven incident response agent - Trigger → Enrich → Reason → Act → Emit."""

import json
import logging

from strands import Agent, tool

from bedrock_agentcore.runtime import BedrockAgentCoreApp

log = logging.getLogger(__name__)
app = BedrockAgentCoreApp()


# --- Tools (Enrich + Act phases) ---


@tool
def get_service_health(service_name: str) -> dict:
    """Check the health status of a service.

    Args:
        service_name: Name of the service to check (e.g., 'checkout-api').

    Returns:
        Service health information including status, error rate, and latency.
    """
    # Replace with real monitoring API in production
    return {
        "status": "success",
        "content": [
            {
                "text": json.dumps(
                    {
                        "service": service_name,
                        "status": "degraded",
                        "error_rate_percent": 12.5,
                        "p99_latency_ms": 2400,
                        "healthy_instances": 2,
                        "total_instances": 4,
                    }
                )
            }
        ],
    }


@tool
def restart_service(service_name: str, reason: str) -> dict:
    """Restart a service to recover from degraded state.

    Args:
        service_name: Name of the service to restart.
        reason: Explanation for why the restart is needed.

    Returns:
        Restart result including new instance count and status.
    """
    log.info("Restarting %s: %s", service_name, reason)
    # Replace with real orchestration API in production
    return {
        "status": "success",
        "content": [
            {
                "text": json.dumps(
                    {
                        "action": "restart",
                        "service": service_name,
                        "result": "completed",
                        "new_instance_count": 4,
                    }
                )
            }
        ],
    }


@tool
def notify_oncall(message: str, severity: str) -> dict:
    """Send a notification to the on-call engineer.

    Args:
        message: Notification message content.
        severity: Alert severity - 'low', 'medium', or 'high'.

    Returns:
        Notification delivery confirmation.
    """
    log.info("Notifying on-call [%s]: %s", severity, message)
    return {
        "status": "success",
        "content": [{"text": f"Notification sent (severity={severity})"}],
    }


# --- System prompt (Reason phase) ---

SYSTEM_PROMPT = """You are an IT incident response agent. When you receive an
incident event, follow this protocol:

1. ENRICH: Use get_service_health to understand the current state.
2. REASON: Analyze the health data and determine the best action.
3. ACT: If the service is degraded, restart it. If critical, also notify on-call.
4. EMIT: Summarize what you did and the outcome.

Rules:
- Only restart services that are in 'degraded' or 'down' status.
- Always notify on-call for 'high' severity incidents.
- Be concise in your summary - operations teams need quick answers."""


@app.entrypoint
def invoke(payload, context):
    """Agent entrypoint - processes incident events from EventBridge."""
    # Handle agentcore dev payload wrapping
    if "prompt" in payload and "service_name" not in payload:
        prompt_value = payload["prompt"]
        if isinstance(prompt_value, str):
            try:
                parsed = json.loads(prompt_value)
                if isinstance(parsed, dict) and "service_name" in parsed:
                    payload = parsed
            except (json.JSONDecodeError, TypeError):
                pass

    # Build the prompt from the event payload
    if "service_name" in payload:
        prompt = (
            f"Incident received:\n"
            f"- Service: {payload['service_name']}\n"
            f"- Event: {payload.get('event_type', 'unknown')}\n"
            f"- Severity: {payload.get('severity', 'medium')}\n"
            f"- Description: {payload.get('description', 'No description')}\n\n"
            f"Follow the incident response protocol."
        )
    else:
        prompt = payload.get("prompt", "No event received.")

    agent = Agent(
        model="us.anthropic.claude-sonnet-4-20250514-v1:0",
        system_prompt=SYSTEM_PROMPT,
        tools=[get_service_health, restart_service, notify_oncall],
    )

    result = agent(prompt)
    return {"response": result.message}


app.run()
```

### The 5-Step Pattern in Action

```
① TRIGGER  → EventBridge delivers "high_error_rate" event
② ENRICH   → Agent calls get_service_health("checkout-api")
③ REASON   → LLM sees degraded + high severity → decides to restart + notify
④ ACT      → Agent calls restart_service() and notify_oncall()
⑤ EMIT     → Agent returns structured summary of actions taken
```

Your automation scripts are brittle. They break on edge cases, can't reason about ambiguous inputs, and require constant maintenance. AgentCore workflow agents replace rigid if-then-else chains with LLM-powered reasoning that adapts to context. The platform handles infrastructure, security, and operational concerns.

### The 5-Step Pattern: Trigger → Enrich → Reason → Act → Emit

Every workflow automation agent follows a consistent execution pattern. This maps traditional event-driven enrichment into a cognition-augmented loop. Where scripts need explicit branching for every case, the LLM reasons over the enriched context and decides the best action dynamically.

## Your Journey to Production

From event handler to autonomous workflow agent in five stages.

1. **Define Your Trigger** - Identify the event that starts the workflow (alert, ticket, schedule, webhook).
2. **Build Your Tools** - Wrap your APIs, databases, and services as Lambda-backed MCP tools with typed schemas.
3. **Implement the Agent** - Write the system prompt, wire tools, and define the reasoning loop with Strands SDK.
4. **Add Guardrails** - Configure Cedar policies to bound the agent's autonomy. Set up online evaluations.
5. **Deploy & Monitor** - Push to AgentCore Runtime. Monitor tool selection accuracy and goal success via CloudWatch.

## How Workflow Agents Differ from Conversational Agents

Understanding when to use each archetype:

<div className="fancy-table fancy-table--auto-first">

| Dimension              | Conversational Agent                   | Workflow Automation Agent                         |
| ---------------------- | -------------------------------------- | ------------------------------------------------- |
| Trigger                | User message (human-initiated)         | System event (machine-initiated)                  |
| Session duration       | Minutes to hours (multi-turn)          | Seconds to minutes (single invocation)            |
| Identity               | End-user token exchange (acts as user) | Service identity (acts as system)                 |
| Memory                 | Session + long-term per user           | Cross-invocation context per entity               |
| Streaming              | Token-by-token to UI                   | Optional - results often go to downstream systems |
| Primary output         | Natural language response to human     | Actions taken + structured events emitted         |
| Scaling pattern        | Concurrent sessions (many users)       | Event throughput (many events per second)         |
| Key evaluation metrics | Helpfulness, Correctness               | GoalSuccessRate, TrajectoryMatch, Correctness     |

</div>

## Event Processing Model

Workflow agents process events asynchronously. The trigger Lambda receives the event, invokes the AgentCore Runtime, and the agent handles reasoning and action.

<div className="fancy-table fancy-table--auto-first">

| Capability            | What AgentCore Provides                                                         |
| --------------------- | ------------------------------------------------------------------------------- |
| Event ingestion       | Lambda trigger receives from EventBridge, SNS, SQS, S3, or API Gateway.         |
| Payload normalization | Trigger Lambda extracts key fields and forwards structured JSON to Runtime.     |
| Idempotency           | Agent can check if event was already processed via DynamoDB or Memory.          |
| Retry with backoff    | DLQ captures failed invocations for replay. CloudWatch alarms on DLQ depth.     |
| Concurrent processing | Multiple events processed in parallel - each gets its own microVM.              |
| Timeout handling      | Runtime sessions have configurable max duration (default 15 min for workflows). |

</div>

### Trigger Lambda Pattern

The trigger Lambda is the bridge between your event source and AgentCore Runtime:

```python
import json
import os

import boto3

# Initialize the Bedrock AgentCore client
agent_core_client = boto3.client('bedrock-agentcore')

def handler(event, context):
    """Receives event from EventBridge/SNS/SQS, invokes AgentCore Runtime."""
    # Extract relevant fields from the event source
    detail = event.get("detail", event)

    payload = {
        "entity_id": detail["entity_id"],
        "event_type": detail["event_type"],
        "priority": detail.get("priority", "MEDIUM"),
        "timestamp": detail.get("timestamp"),
        "context": detail.get("context", {}),
    }

    response = agent_core_client.invoke_agent_runtime(
        agentRuntimeArn=os.environ["RUNTIME_ARN"],
        runtimeSessionId=f"event-{detail['entity_id']}",
        payload=json.dumps(payload).encode(),
    )

    return {"statusCode": 200, "body": "Agent invoked"}
```

## Memory for Workflow Agents

Workflow agents use memory differently than conversational agents. Instead of multi-turn conversation history, they remember facts about *entities* (tickets, incidents, devices) across invocations.

<div className="fancy-table fancy-table--auto-first">

| Strategy         | Use Case                                                       | Example                                             |
| ---------------- | -------------------------------------------------------------- | --------------------------------------------------- |
| SEMANTIC         | Remember facts about entities that accumulate over time        | "INC-001 has been escalated twice before"           |
| SUMMARIZATION    | Condense prior actions into context for the current invocation | "Last time this device alerted, we restarted nginx" |
| None (stateless) | Simple event processing where each invocation is independent   | "Route this support email to the right queue"       |

</div>

### When to Use Memory vs. External State

<div className="fancy-table fancy-table--auto-first">

| Question                                         | If Yes → Use...             |
| ------------------------------------------------ | --------------------------- |
| Does the agent need context from prior events?   | AgentCore Memory (SEMANTIC) |
| Does the agent track entity state across events? | DynamoDB + Memory           |
| Is each event fully self-contained?              | No memory needed            |
| Does the agent learn user preferences over time? | Memory (long-term)          |

</div>

## Bounded Autonomy: Policy Engine

The single most important differentiator for production workflow agents. Without policy enforcement, an agent with access to infrastructure tools is a liability. With it, the agent operates within a provable boundary.

<div className="fancy-table fancy-table--auto-first">

| Capability                  | Detail                                                                     |
| --------------------------- | -------------------------------------------------------------------------- |
| Tool-level access control   | Allow or deny specific tools based on Cedar policies.                      |
| Condition-based enforcement | Restrict tool use based on request context (time, entity type, priority).  |
| ENFORCE vs MONITOR modes    | Start with MONITOR to observe decisions; switch to ENFORCE for production. |
| Audit trail                 | Every policy evaluation is logged with full context in CloudWatch.         |
| Multi-policy composition    | Combine multiple policies - deny always wins over permit.                  |

</div>

### Example: Priority-Based Autonomy

```cedar
// High-priority incidents: allow remediation actions
permit(
  principal is AgentCore::IamEntity,
  action == AgentCore::Action::"RemediationTools___restart_service",
  resource == AgentCore::Gateway::"arn:aws:bedrock-agentcore:us-west-2:123456789012:gateway/incident-gateway"
)
when {
  context.input.priority == "HIGH"
};

// Low-priority: only allow read-only diagnostic tools
permit(
  principal is AgentCore::IamEntity,
  action == AgentCore::Action::"DiagnosticTools___get_metrics",
  resource == AgentCore::Gateway::"arn:aws:bedrock-agentcore:us-west-2:123456789012:gateway/incident-gateway"
)
when {
  context.input.priority == "LOW"
};
```

:::info Why this matters
Without bounded autonomy, you get one of two outcomes: over-permissive agents that can cause outages when they make mistakes, or under-permissive agents that require human approval for every action, defeating the purpose of automation. Cedar policies let you precisely define the boundary - the agent reasons freely within its allowed actions, and the platform prevents it from exceeding them, regardless of what the LLM decides.
:::

## Tool Design for Workflow Agents

Tools are the hands of the agent. Well-designed tools make the difference between an agent that works and one that hallucinates actions.

<div className="fancy-table fancy-table--auto-first">

| Principle                        | Why                                                                       |
| -------------------------------- | ------------------------------------------------------------------------- |
| One tool = one action            | Compound tools confuse the LLM. Split "get and update" into two tools.    |
| Descriptive names and docstrings | The LLM decides tool selection based on name + description. Be specific.  |
| Validate all inputs              | The LLM sends arbitrary values. Check types, formats, and bounds.         |
| Return errors as values          | Don't raise exceptions. Return `{"error": "..."}` so the agent can adapt. |
| Typed schemas                    | Every tool gets a JSON schema defining inputs. No "catch-all" parameters. |
| Idempotent where possible        | Agent might retry on failure. Make tools safe to call multiple times.     |

</div>

### Tool Hosting: Co-Located vs. Gateway

<div className="fancy-table fancy-table--auto-first">

| Approach       | When to Use                                            | Trade-off                       |
| -------------- | ------------------------------------------------------ | ------------------------------- |
| Co-located     | Simple tools, few dependencies, fast iteration         | No separate deployment or IAM   |
| Gateway target | Complex or shared tools, many tools, cross-agent reuse | More infrastructure, more reuse |

</div>

The Gateway aggregates all MCP targets into a single virtual MCP server, exposing one consolidated `tools/list` to the agent. **Semantic tool search** lets the agent select the right tool even when hundreds are registered - important for autonomous workflows that span many enterprise systems.

<div className="fancy-table fancy-table--auto-first">

| Target Type               | Use For                                                                |
| ------------------------- | ---------------------------------------------------------------------- |
| Lambda function           | Custom business logic in any language; gateway invokes and maps to MCP |
| OpenAPI / API Gateway     | Turn an existing REST API into MCP tools with no code                  |
| Smithy model              | Generate tools for AWS services or Smithy-defined APIs                 |
| MCP server                | Connect a remote MCP server's tools, prompts, and resources            |
| Integrations / connectors | Pre-built templates and connectors for common tools                    |

</div>

The Gateway separates the two directions of authentication, which matters for autonomous agents that run without a human in the loop:

- **Inbound (agent → gateway):** use **IAM (SigV4)** so the agent calls as a service identity. OAuth (JWT) is also supported; `authenticate-only` validates the token but defers authorization to the target.
- **Outbound (gateway → backend):** Lambda and Smithy targets use the gateway's execution role; OpenAPI and MCP-server targets use an **AgentCore credential provider** (API key, OAuth, or SigV4), so credentials for Jira, ServiceNow, or internal APIs stay in the gateway rather than the agent.

:::info Beyond tools
Gateway targets come in three categories. **MCP targets** (the tools above) are aggregated into the virtual MCP server. **HTTP targets** proxy directly to other agents or A2A services - useful when a workflow agent orchestrates specialized sub-agents. **Inference targets** route LLM traffic to multiple model providers through one endpoint.
:::

### Example: Well-Designed Tool

```python
@tool
def get_incident_details(incident_id: str) -> str:
    """Retrieve full details for an incident by its ID.

    Call this tool when you need to understand the current state,
    severity, affected services, and timeline of an incident.

    Args:
        incident_id: The incident identifier (format: INC-NNNNN).
    """
    if not incident_id or not re.match(r"^INC-\d{3,7}$", incident_id):
        return "Error: incident_id must match format INC-NNNNN"

    try:
        item = incidents_table.get_item(Key={"id": incident_id}).get("Item")
        if not item:
            return f"Error: Incident {incident_id} not found"
        return json.dumps(item, default=str)
    except Exception as exc:
        return f"Error: {type(exc).__name__}: {exc}"
```

## Evaluations

Workflow agents make real decisions with real consequences. You need to know - continuously, not just at launch - whether those decisions are correct. Conversational agents have users who immediately notice bad answers. Workflow agents operate in the background, so bad decisions can compound silently for days before anyone notices.

### Built-in Evaluators

AgentCore provides built-in evaluators that score agent behavior against your session telemetry. Trajectory evaluators use **programmatic scoring (no LLM calls, zero token cost)**, while GoalSuccessRate and Correctness use LLM-as-a-Judge.

<div className="fancy-table fancy-table--auto-first">

| Evaluator                 | Level   | Ground Truth Field   | What It Measures                                                       |
| ------------------------- | ------- | -------------------- | ---------------------------------------------------------------------- |
| GoalSuccessRate           | Session | `assertions`         | Behavior satisfies natural-language assertions (LLM-as-Judge)          |
| Correctness               | Trace   | `expectedResponse`   | Response matches the expected answer (LLM-as-Judge)                    |
| TrajectoryExactOrderMatch | Session | `expectedTrajectory` | Exact tool sequence - same tools, same order, no extras (programmatic) |
| TrajectoryInOrderMatch    | Session | `expectedTrajectory` | Expected tools appear in order; extras allowed between (programmatic)  |
| TrajectoryAnyOrderMatch   | Session | `expectedTrajectory` | All expected tools present, any order, extras allowed (programmatic)   |
| Custom (LLM-as-judge)     | -       | placeholders         | Your domain-specific criteria (e.g., "followed escalation policy")     |

</div>

### Ground Truth Evaluations

Ground truth is the known-correct answer or expected behavior for a given input - the "gold standard" you compare actual results against. You provide reference inputs alongside session spans when calling the Evaluate API, and the service scores actual behavior against expected behavior.

<div className="fancy-table fancy-table--auto-first">

| Field                | Scope   | Description                                                        |
| -------------------- | ------- | ------------------------------------------------------------------ |
| `expectedResponse`   | Trace   | Expected agent response for a specific turn (scoped by `traceId`)  |
| `assertions`         | Session | Natural-language statements that should be true about the behavior |
| `expectedTrajectory` | Session | Expected sequence of tool-call names for the session               |

</div>

Ground truth fields are optional. If you omit them, evaluators fall back to their ground-truth-free mode - for example, `Builtin.Correctness` still works without `expectedResponse`, evaluating on context alone. For workflow agents, build a benchmark dataset of past events with known-correct outcomes to catch regressions before they reach production.

:::info Prerequisites
Evaluations require an agent deployed on AgentCore Runtime with observability enabled (or a supported framework - Strands Agents or LangGraph - configured for AgentCore Observability), **Transaction Search enabled in CloudWatch**, and Python 3.10+.
:::

### Running an Evaluation

Use the AgentCore SDK (or the `agentcore run eval` CLI) to evaluate a session against ground truth:

```python
from bedrock_agentcore.evaluation import EvaluationClient, ReferenceInputs

client = EvaluationClient(region_name=REGION)

results = client.run(
    evaluator_ids=[
        "Builtin.GoalSuccessRate",
        "Builtin.TrajectoryExactOrderMatch",
    ],
    agent_id=AGENT_ID,
    session_id=SESSION_ID,
    reference_inputs=ReferenceInputs(
        assertions=[
            "Agent used the remediation tool for the HIGH-priority incident",
            "Agent did not call any destructive infrastructure tools",
        ],
        expected_trajectory=["get_incident_details", "restart_service"],
    ),
)

for r in results:
    print(f"{r['evaluatorId']}: {r['value']} ({r['label']})")
```

:::tip Cost-efficient quality gates
Trajectory evaluators are programmatic (zero token cost), so you can run them on 100% of invocations cheaply. Reserve the LLM-judged evaluators (GoalSuccessRate, Correctness) for sampled traffic or high-priority events.
:::

## Workflow-Specific Configuration

The same patterns are used across archetypes. What differs is *how you configure AgentCore services* for workflow automation workloads.

<div className="fancy-table fancy-table--auto-first">

| AgentCore Service | Workflow Configuration                               | Why It Matters                                             |
| ----------------- | ---------------------------------------------------- | ---------------------------------------------------------- |
| **Identity**      | Service principal (client credentials or SigV4)      | Agent acts as a system, not a user                         |
| **Memory**        | SEMANTIC per entity, optional SUMMARIZATION          | Cross-invocation context for recurring events              |
| **Runtime**       | Short sessions (minutes), no streaming required      | Event processing, not interactive conversation             |
| **Policy Engine** | Cedar policies in ENFORCE mode                       | Bounded autonomy is mandatory for production automation    |
| **Evaluations**   | Trajectory 100% programmatic; LLM-judged sampled     | Silent failures: no user to notice bad decisions           |
| **Observability** | Per-invocation tracing with entity and event context | Debug "why did the agent take that action on INC-12345?"   |
| **Gateway**       | SigV4 inbound; credential provider outbound          | Calls tools as a service identity; secrets stay in gateway |

</div>

## Operational Patterns

### Error Handling: Non-Fatal by Default

The agent's primary job is to process the event and take action. Secondary operations (logging, notifications) should never kill the primary workflow:

```python
def _persist_result(result: dict) -> None:
    """Write result to DDB. Non-fatal: if this fails, the agent still acts."""
    try:
        table.put_item(Item=result)
    except Exception as exc:
        log.warning("Failed to persist (non-fatal): %s", exc)
```

### Dead Letter Queue + Alarms

Every trigger Lambda should have a DLQ for failed invocations and a CloudWatch alarm on DLQ depth:

```typescript
const dlq = new sqs.Queue(this, 'TriggerDLQ', {
  retentionPeriod: Duration.days(14),
});
const triggerFn = new lambda.Function(this, 'Trigger', {
  deadLetterQueue: dlq,
  retryAttempts: 2,
});
new cloudwatch.Alarm(this, 'DLQAlarm', {
  metric: dlq.metricApproximateNumberOfMessagesVisible(),
  threshold: 1,
  evaluationPeriods: 1,
});
```

### Cost Routing (Model Selection)

Not every event needs Claude Sonnet. Route by priority:

```python
def load_model(priority: str = "MEDIUM") -> BedrockModel:
    """LOW → Haiku (fast/cheap), MEDIUM+ → Sonnet (full reasoning)."""
    model_id = FAST_MODEL_ID if priority == "LOW" else AGENT_MODEL_ID
    return BedrockModel(model_id=model_id)
```

## Multi-Tenant Isolation

Enterprise event-driven workloads often serve multiple tenants, business units, or customers from shared infrastructure. AgentCore provides isolation at every layer.

<div className="fancy-table fancy-table--auto-first">

| Layer         | Isolation Mechanism                                                       |
| ------------- | ------------------------------------------------------------------------- |
| Compute       | Dedicated microVM per invocation. No shared processes between tenants.    |
| Memory        | Namespace-per-entity. One tenant cannot retrieve another's memory events. |
| Gateway/Tools | Scoped credentials per invocation. Each tool call is bound to the caller. |
| Observability | Traces carry tenant/entity context. Filter by tenant in CloudWatch.       |
| Data at rest  | Encryption with customer-managed keys (CMK) supported.                    |

</div>

:::info Why this matters
For multi-tenant SaaS processing events from different customers, use the entity/tenant ID in the memory namespace and session ID so there is zero cross-contamination between tenants even when events are processed concurrently.
:::
