# Workflow Agents

:::tip Who this is for
Builders evaluating whether an event-driven workflow agent fits their automation problem. If you've already decided, jump straight to the [workflow quickstart](/docs/workloads/workflow/quickstart); if you're still comparing patterns, see the [workloads overview](/docs/workloads/overview).
:::

Event-driven automation agents that reason, act, and adapt. AgentCore runs your workflow agents at scale with built-in security, observability, and bounded autonomy, replacing brittle scripts with intelligent automation.

---

## What Is It?

A workflow agent is an autonomous automation system triggered by events, not humans. When an alert fires, a document arrives, or a schedule ticks, the agent wakes up, gathers context, reasons about the situation, takes action, and goes back to sleep. Unlike traditional automation scripts with rigid if-then-else chains, workflow agents use LLM reasoning to handle ambiguous inputs, adapt to edge cases, and make judgment calls within defined guardrails.

---

## Common Use Cases

- **Claims processing / adjudication** — Insurance or healthcare claims arrive as events. The agent enriches with policy data, reasons about coverage rules, approves/denies within policy limits, and escalates edge cases to a human adjuster.
- **IT incident response / auto-remediation** — Monitoring alert fires. Agent pulls service health, correlates with recent changes, executes runbook steps (restart, scale, failover), and notifies on-call only when human judgment is needed.
- **Document intake and routing** — Documents land in S3 or arrive via email. Agent classifies document type, extracts key fields, routes to the appropriate queue, and triggers downstream workflows.
- **Compliance drift detection** — Scheduled scan finds configuration drift. Agent assesses severity, auto-remediates known patterns, and creates tickets for novel findings.
- **Email / ticket triage and auto-response** — Inbound support emails are classified by intent and urgency. Auto-responded if the answer is clear, or routed to the right team with a pre-drafted response.
- **Order exception handling** — Fulfillment system flags a stuck order. Agent investigates root cause (inventory, payment, shipping status), resolves if possible, or escalates with full context.

## When to Choose Workflow

Choose this workload when:

- A system event is the trigger (alert, webhook, schedule, file upload, message queue)
- The agent needs to make decisions and take actions autonomously
- You need bounded autonomy: the agent should act within defined guardrails, not freely
- The primary output is actions taken and events emitted, not chat messages
- Each invocation is short-lived (seconds to minutes), not a long conversation

For a side-by-side comparison with Conversational and Coding patterns, see the [Workloads overview comparison table](/docs/workloads/overview#how-they-compare).

## Strengths and Limitations

<div className="fancy-table">

| Strengths                                              | Limitations                                                      |
|--------------------------------------------------------|------------------------------------------------------------------|
| [Scale-to-zero](https://docs.aws.amazon.com/wellarchitected/latest/agentic-ai-lens/agentcost06-bp03.html) (no idle compute between events) | Not suited for multi-turn human conversations                    |
| [Bounded autonomy via Cedar policies](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-authorization-flow.html) | Requires upfront policy design to constrain behavior             |
| Event-driven fits existing AWS infrastructure          | More complex trigger setup than a simple API endpoint            |
| LLM reasoning handles edge cases scripts cannot        | Non-deterministic: same event may produce different actions      |
| Full audit trail for every decision                    | Higher latency than pure rule-based automation                   |
| Programmatic evaluations at zero token cost            | Evaluation dataset requires curating ground-truth examples       |

</div>

## The 5-Step Execution Pattern

Every workflow automation agent follows a consistent execution loop:

<div className="arch-flow">
  <span className="arch-flow-step">① Trigger (event arrives)</span>
  <span className="arch-flow-arrow">→</span>
  <span className="arch-flow-step">② Enrich (gather context)</span>
  <span className="arch-flow-arrow">→</span>
  <span className="arch-flow-step">③ Reason (LLM decides)</span>
  <span className="arch-flow-arrow">→</span>
  <span className="arch-flow-step">④ Act (execute via tool)</span>
  <span className="arch-flow-arrow">→</span>
  <span className="arch-flow-step">⑤ Emit (publish event)</span>
</div>

Where scripts need explicit branching for every case, the LLM reasons over the enriched context and decides the best action dynamically.

## When Not to Use This Pattern

**Skip the Workflow pattern when:**

- The automation logic is simple and deterministic (a few if/else conditions, no reasoning needed). A scheduled AWS Lambda function with direct API calls is simpler, cheaper, and easier to debug.
- A human needs real-time responses during the process. Use the [Conversational pattern](/docs/workloads/conversational/overview) instead.
- The primary output is code, tests, or PRs. Use the [Coding pattern](/docs/workloads/coding/overview) instead.
- You cannot define bounded autonomy upfront. If you cannot describe what actions the agent is and is not allowed to take, the policy design will be hard. Start with a deterministic script and graduate to an agent when the edge cases accumulate.
- Tasks consistently exceed the short-lived session window. For long-running background jobs (hours), consider the Coding pattern or orchestrating multiple short-lived workflow agent invocations.
