# Event Processing Model

Workflow agents process events asynchronously. An event source delivers a trigger, a Lambda normalizes the payload and invokes the AgentCore Runtime, and the agent handles reasoning and action.

## Platform Capabilities

<div className="fancy-table fancy-table--auto-first">

| Capability            | What AgentCore Provides                                                          |
|-----------------------|----------------------------------------------------------------------------------|
| Event ingestion       | Lambda trigger receives from EventBridge, SNS, SQS, S3, or API Gateway.         |
| Payload normalization | Trigger Lambda extracts key fields and forwards structured JSON to Runtime.      |
| Idempotency           | Agent can check if event was already processed via DynamoDB or Memory.           |
| Retry with backoff    | DLQ captures failed invocations for replay. CloudWatch alarms on DLQ depth.     |
| Concurrent processing | Multiple events processed in parallel. Each gets its own microVM.              |
| Timeout handling      | Runtime sessions have configurable max duration (default 15 min for workflows).  |

## Trigger Lambda Pattern

The trigger Lambda is the bridge between your event source and AgentCore Runtime:

```python
import json
import os

import boto3

# Initialize the Bedrock AgentCore client
agent_core_client = boto3.client('bedrock-agentcore')

def handler(event, context):
    """Receives event from EventBridge/SNS/SQS, invokes AgentCore Runtime."""
    # Extract relevant fields from the event source
    detail = event.get("detail", event)

    payload = {
        "entity_id": detail["entity_id"],
        "event_type": detail["event_type"],
        "priority": detail.get("priority", "MEDIUM"),
        "timestamp": detail.get("timestamp"),
        "context": detail.get("context", {}),
    }

    response = agent_core_client.invoke_agent_runtime(
        agentRuntimeArn=os.environ["RUNTIME_ARN"],
        runtimeSessionId=f"event-{detail['entity_id']}",
        payload=json.dumps(payload).encode(),
    )

    return {"statusCode": 200, "body": "Agent invoked"}
```

|----------------|-------------------------------------------------------------|---------------------|

## The 5-Step Pattern

Every workflow automation agent follows this execution loop:

<div className="arch-flow">
  <span className="arch-flow-step">① Trigger (event arrives)</span>
  <span className="arch-flow-arrow">→</span>
  <span className="arch-flow-step">② Enrich (gather context)</span>
  <span className="arch-flow-arrow">→</span>
  <span className="arch-flow-step">③ Reason (LLM decides)</span>
  <span className="arch-flow-arrow">→</span>
  <span className="arch-flow-step">④ Act (execute via tool)</span>
  <span className="arch-flow-arrow">→</span>
  <span className="arch-flow-step">⑤ Emit (publish event)</span>
</div>

**① Trigger** — An event arrives from one of the sources above. The trigger Lambda normalizes it into a structured payload.

**② Enrich** — The agent calls read-only tools to gather context: service health, ticket history, user profile, related incidents.

**③ Reason** — The LLM analyzes the enriched context and determines the best course of action. This is where scripts break and agents shine: handling edge cases, ambiguous inputs, and novel situations.

**④ Act** — The agent executes actions via tools: restart a service, update a ticket, send a notification, create a resource.

**⑤ Emit** — The agent publishes a completion event (to EventBridge, SNS, or a downstream system) with the outcome summary. This enables event chaining and audit trails.
