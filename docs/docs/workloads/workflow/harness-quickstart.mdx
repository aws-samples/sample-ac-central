# Quick Start: Workflow Agent on Harness

Deploy the reasoning step of an event pipeline using configuration only — no agent code.

| | |
|---|---|
| **Who this is for** | Developers adding an LLM triage/decision step to event-driven automation |
| **Time** | ~10 minutes |
| **What you'll build** | An incident triage step that classifies events and emits structured JSON |
| **Safety level** | Creates real AWS resources; the agent only classifies — it takes no actions |

---

## Harness vs. Runtime for Workflow Agents

The [Runtime quickstart](/docs/workloads/workflow/quickstart) implements the full Trigger → Enrich → Reason → Act → Emit loop in code, with Python tool functions for the Enrich and Act phases. An **AgentCore Harness** is a managed agent loop declared as configuration — a natural fit when your pipeline needs a *bounded reasoning step* between systems that already exist:

```
① TRIGGER  → EventBridge/SQS delivers the incident event
② REASON   → Harness classifies severity and recommends action   ← this page
③ EMIT     → Structured JSON verdict returned to the pipeline
④ ACT      → Downstream automation (Step Functions, Lambda) executes the verdict
```

Execution limits — a core workflow concern — become config fields instead of code:

<div className="fancy-table fancy-table--auto-first">

| Concern | Runtime (code) | Harness (config) |
|---|---|---|
| Agent loop | You write it in `main.py` | Managed, powered by Strands |
| Iteration/time caps | You implement them | `maxIterations`, `timeoutSeconds` in `harness.json` |
| Tools | Local Python functions | Declared config: gateway, MCP, browser, code interpreter |

</div>

Choose the harness when the reasoning step is declarative and actions run downstream. Choose Runtime when Enrich/Act require custom local tool code in the same loop. See the [AWS harness vs. Runtime comparison](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-vs-runtime.html) for the full grid.

## Step 1: Create the Project and Harness

Run this from the directory where you want the project folder created. The system prompt defines the triage contract, and the flags cap execution — no memory is configured because event processing is stateless:

```bash
npm install -g @aws/agentcore@0.24.1
agentcore create --project-name incidenttriage --no-agent
cd incidenttriage
agentcore add harness \
  --name IncidentTriage \
  --model-provider bedrock \
  --max-iterations 6 \
  --timeout 120 \
  --system-prompt "You are an automated incident triage step in an event pipeline. You receive one incident event as JSON. Analyze it and respond with ONLY a JSON object, no prose, matching this shape: {\"service\": string, \"severity\": \"low\"|\"medium\"|\"high\", \"probable_cause\": string, \"recommended_action\": string, \"page_oncall\": boolean}. Set page_oncall to true only for high severity. Base severity on the event's error rate and impact."
```

---

## Step 2: Review the Configuration

The command wrote everything to `app/IncidentTriage/harness.json`:

```json
{
  "name": "IncidentTriage",
  "model": {
    "provider": "bedrock",
    "modelId": "global.anthropic.claude-sonnet-4-6"
  },
  "systemPrompt": "You are an automated incident triage step in an event pipeline. ...",
  "tools": [],
  "skills": [],
  "memory": {
    "mode": "disabled"
  },
  "maxIterations": 6,
  "timeoutSeconds": 120
}
```

`maxIterations` caps the agent loop and `timeoutSeconds` bounds total execution — the harness equivalents of the retry and runaway-loop guards you would otherwise code by hand. Memory stays `disabled`: each event is an independent invocation.

Validate the configuration:

```bash
agentcore validate
```

## Step 3: Deploy

```bash
agentcore deploy
```

Deployment creates AWS resources and may incur charges. Check status:

```bash
agentcore status
```

## Step 4: Send Test Events

Simulate the Trigger step by invoking the harness with incident events. AgentCore requires session IDs of at least 33 characters; event pipelines typically use a fresh session per event:

```bash
# High-severity event
agentcore invoke --harness IncidentTriage --session-id "$(uuidgen)" \
  '{"service_name": "checkout-api", "event_type": "high_error_rate", "error_rate_percent": 12.5, "healthy_instances": 2, "total_instances": 4, "description": "Error rate exceeded 10% threshold"}'
# Expected: JSON verdict with "severity": "high" and "page_oncall": true

# Low-severity event
agentcore invoke --harness IncidentTriage --session-id "$(uuidgen)" \
  '{"service_name": "search-api", "event_type": "elevated_latency", "error_rate_percent": 0.4, "healthy_instances": 6, "total_instances": 6, "description": "P99 latency increased 15% over baseline"}'
# Expected: JSON verdict with "severity": "low" and "page_oncall": false
```

A verified high-severity response:

```json
{
  "service": "checkout-api",
  "severity": "high",
  "probable_cause": "50% of instances (2 of 4) are unhealthy, causing elevated error rates above the 10% threshold at 12.5%. ...",
  "recommended_action": "1) Immediately inspect logs and health checks on the 2 unhealthy instances. ...",
  "page_oncall": true
}
```

:::note Parse defensively downstream
The model may wrap the JSON in a Markdown code fence. Downstream consumers (Lambda, Step Functions) should strip fences before parsing, and treat unparseable output as a triage failure to route to a dead-letter queue. For production pipelines, validate the verdict against a schema before acting on it.
:::

## Wiring Real Event Sources

`agentcore invoke` stands in for the Trigger step. In production, event sources call the harness through the `InvokeHarness` API — for example, an EventBridge rule targeting a small Lambda that forwards the event:

```python
import boto3, json, uuid

client = boto3.client("bedrock-agentcore")

def handler(event, _context):
    response = client.invoke_harness(
        harnessArn=HARNESS_ARN,
        runtimeSessionId=str(uuid.uuid4()),
        messages=[{"role": "user", "content": [{"text": json.dumps(event["detail"])}]}],
    )
    # Collect the streamed verdict, then hand it to the Act step
```

See [Event Processing](/docs/workloads/workflow/event-processing) for source-by-source guidance and [Bounded Autonomy](/docs/workloads/workflow/bounded-autonomy) for policy enforcement before any Act step runs.

## Placeholders in This File

- `incidenttriage`, `IncidentTriage` — example project and harness names; both become part of generated AWS resource names
- `checkout-api`, `search-api` — sample service names in the test events; replace with your real services
- `$(uuidgen)` — generates a valid session ID (33+ characters required); use a fresh one per event
- `global.anthropic.claude-sonnet-4-6` — default model written by the CLI in `0.24.1`; substitute your preferred Bedrock model ID
- `HARNESS_ARN` — your deployed harness ARN, printed by `agentcore deploy` and `agentcore status`

## What This Creates and What It Costs

| Resource | Notes |
|---|---|
| AgentCore harness | Managed agent-loop configuration; runs inside Runtime microVMs |
| IAM execution role | Role the harness uses to call the model |
| CloudWatch log groups | Receives invocation logs and traces |

**Main cost drivers:**
- **Model inference tokens** — every event calls the configured Bedrock model
- **Runtime execution seconds** — the harness executes inside Runtime; billed per second
- **Log ingestion** — CloudWatch charges per GB ingested and stored

**Scale-to-zero does not mean zero cost.** CloudWatch log retention accrues charges with no traffic. Remove resources when you're done experimenting.

## Cleanup

```bash
# From your project directory; review the confirmation prompt before continuing
agentcore remove all
agentcore deploy
```

Verify resources are gone:

```bash
agentcore status
# Expected: no harnesses listed
```

CloudWatch log groups are retained; delete them manually to stop log storage charges. If cleanup reports errors, see [Cleanup Failures](/docs/reference/troubleshooting#cleanup-failures).
