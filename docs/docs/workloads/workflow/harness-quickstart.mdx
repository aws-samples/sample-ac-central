## Harness vs. Runtime for workflow agents

The [Runtime quickstart](/docs/workloads/workflow/quickstart) implements the full Trigger → Enrich → Reason → Act → Emit loop in code, with Python tool functions for the Enrich and Act phases. An **AgentCore Harness** is a managed agent loop declared as configuration — a natural fit when your pipeline needs a *bounded reasoning step* between systems that already exist:

```
① TRIGGER  → EventBridge/SQS delivers the event
② REASON   → Harness classifies and emits a structured verdict   ← this page
③ ACT      → Downstream automation executes the verdict
```

### When execution limits are config, not code

Execution limits — a core workflow concern — become config fields instead of hand-written guards:

<div className="fancy-table fancy-table--auto-first">

| Concern | Runtime (code) | Harness (config) |
|---|---|---|
| Agent loop | You write it in `main.py` | Managed, powered by Strands |
| Iteration/time caps | You implement them | `maxIterations`, `timeoutSeconds` in `harness.json` |
| Tools | Local Python functions | Declared config: gateway, MCP, browser, code interpreter |

</div>

Choose the harness when the reasoning step is declarative and actions run downstream. Choose Runtime when Enrich/Act require custom local tool code in the same loop. See the [AWS harness vs. Runtime comparison](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-vs-runtime.html) for the full grid.

## Workflow-specific context

The [Harness Getting Started](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/harness-get-started.html) tutorial covers project creation, configuration, deployment, and invocation. The sections below cover what matters specifically for **workflow workloads**:

- **Decision criteria** — when a config-only reasoning step is enough vs. when you need the full Runtime with local tools.
- **Execution-limit mapping** — how `maxIterations` and `timeoutSeconds` replace the runaway-loop and timeout guards you would otherwise code by hand.
- **Event-pipeline positioning** — a harness sits at the Reason step; it does not own Trigger or Act. Downstream systems (Step Functions, Lambda) execute the verdict.
- **Production boundary** — Harness creates a working prototype. Real event-driven pipelines need dead-letter handling, schema validation, and policy enforcement before acting on verdicts. See the [Production Readiness checklist](/docs/operate/production-readiness).

## When to switch to the workflow samples

The Harness path covers bounded reasoning with no local tools. Switch to a [workflow automation sample](https://github.com/awslabs/agentcore-samples/tree/main/02-use-cases/02-workflow-automation-agents) when you need:

- **Event sources** — wiring EventBridge rules, SQS queues, or SNS subscriptions to trigger the agent directly.
- **Durable state** — maintaining context across multiple events or long-running workflows.
- **Action execution in the agent loop** — calling tools that read services, create tickets, or notify on-call as part of the same reasoning pass.

Workflow samples carry their own documented risk profiles. Review each sample's Action_Risk disclosure and apply [bounded autonomy policies](/docs/workloads/workflow/bounded-autonomy) before connecting to production systems.
