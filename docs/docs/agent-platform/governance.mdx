# Governance & Security

:::tip Who this is for
Platform teams implementing governance, policies, and compliance for agent deployments — the two-plane architecture, Cedar policy authoring, identity propagation, and cost attribution.
:::

Autonomous agents introduce a new class of enterprise risk. Unlike traditional software that executes deterministic logic, agents reason, make decisions, and invoke tools dynamically. Without governance, this autonomy can lead to data exfiltration, cost overruns, compliance violations, and reputational damage. This page covers the two-plane governance architecture, the services that provide each layer, and which capabilities are native, preview, or require customer-built integration.

---

## Why Agent Governance

:::caution
An unmonitored agent with broad tool access can - in a single session - access sensitive data, invoke external APIs, generate unauthorized content, and accumulate significant token costs. Traditional application security models are insufficient.
:::

**Key risks that governance addresses:**

<div className="fancy-table">

| Risk                   | Impact                                              | Example                                                    |
| ---------------------- | --------------------------------------------------- | ---------------------------------------------------------- |
| Data Exfiltration      | Sensitive data leaks to unauthorized destinations   | Agent sends PII to an unvetted external API                |
| Cost Overruns          | Uncontrolled token consumption and tool invocations | Recursive agent loop burns through monthly budget in hours |
| Compliance Violations  | Regulatory breach                                   | Agent processes EU citizen data outside approved regions   |
| Hallucination at Scale | Incorrect information propagated to customers       | Customer-facing agent provides fabricated policy details   |
| Unauthorized Actions   | Agent takes actions beyond its intended scope       | Agent modifies production database during a read-only task |

</div>

## Two-Plane Governance Architecture

Effective agent governance separates **policy definition** from **runtime enforcement**. This separation enables centralized policy management with distributed enforcement at the point of execution.

### Governance Plane - Define Policy

The governance plane is where policies are authored, agents are registered, identities are managed, and compliance is monitored.

### AWS Agent Registry - Discovery and Approval Lifecycle

AWS Agent Registry (public preview) is the catalog that answers "what agents, tools, and MCP servers already exist, and are they approved for use." Every record moves through the same status lifecycle, whether it was registered manually or pulled automatically from an MCP/A2A endpoint.

<div className="fancy-table">

| Status             | Meaning                                                                                 |
| ------------------ | --------------------------------------------------------------------------------------- |
| `DRAFT`            | Record created but not yet submitted for review                                         |
| `PENDING_APPROVAL` | Submitted; awaiting reviewer decision (or auto-approval if the registry has it enabled) |
| `APPROVED`         | Discoverable via search and the registry's MCP endpoint                                 |
| `REJECTED`         | Reviewer declined the record; not discoverable                                          |
| `DEPRECATED`       | Previously approved, now retired from active discovery                                  |

</div>

Two integration points make Registry useful as a governance control point, not just a catalog:

- **EventBridge on submission**: when a publisher submits a record for approval, Registry emits an EventBridge notification that can trigger an existing review pipeline (security review, compliance check). The pipeline calls `UpdateRegistryRecordStatus` to approve or reject, so organizations plug Registry into review processes they already run instead of building a new one.
- **MCP-native discovery**: the registry is queryable as an MCP server, so any MCP-compatible client (including IDE agents) can search for approved agents and tools directly, in addition to the console and control-plane API.

:::info
Only `APPROVED` records appear in search results or the registry's MCP endpoint. Approval is eventually consistent. Indexing can take a few seconds up to a few minutes after a record moves to `APPROVED`.
:::

#### Policy vs. Guardrails - Two Different Controls

AgentCore Policy and Bedrock Guardrails both sit in the enforcement path, but they answer different questions and operate at different layers:

<div className="fancy-table">

| Aspect            | AgentCore Policy                                                    | Bedrock Guardrails                                                         |
| ----------------- | ------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| Question answered | Can this principal call this tool on this resource?                 | Is this content safe to send or receive?                                   |
| Layer             | Gateway, before a tool call reaches its target                      | Model input/output, around the inference call                              |
| Language          | Cedar (`permit`/`forbid` over principal, action, resource, context) | Configured policy (denied topics, content filters, PII patterns)           |
| Determinism       | Deterministic - same input always yields the same allow/deny        | Probabilistic scoring against configured thresholds                        |
| Typical use       | "Only the billing role can call `refund_payment`"                   | "Never return unredacted SSNs" or "block discussion of competitor pricing" |

</div>

Both support a **log-only** mode for safe rollout. AgentCore Policy has two independent log-only controls that are easy to conflate: the policy engine's `mode` (`ENFORCE` or `LOG_ONLY`) governs whether the engine enforces anything at all, and each individual policy's `enforcementMode` (`ACTIVE` or `LOG_ONLY`) governs whether that specific policy's decision is enforced. Engine-level `LOG_ONLY` takes precedence. If the engine is in log-only mode, no policy can block a Gateway call, even if that policy's own `enforcementMode` is `ACTIVE`. Use policy-level `LOG_ONLY` to shadow-test one new rule in production. Use engine-level `LOG_ONLY` to observe an entire policy set before turning on enforcement. See [policy enforcement modes](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-enforcement-modes.html) and [testing a policy](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-test-a-policy.html) for step-by-step guidance.

## Identity Propagation Across Agent Hops

In a multi-agent system, the request that started with a human user often passes through several agents and tool calls before it produces a result. If each hop only checks "is the caller a valid agent," you lose the original user's identity along the way, and every downstream authorization decision is made against the wrong principal.

AgentCore Identity's workload identity model is built to prevent that. A workload identity is the stable identity of the agent itself; the `GetWorkloadAccessTokenForUserId` API layers the acting user's identity on top of it, producing a token that is scoped to both "this agent" and "this user." Passing that token (not just the agent's own credentials) to every downstream tool call and sub-agent invocation keeps the original user's identity attached through the full chain:

```python
from bedrock_agentcore.services.identity import IdentityClient

identity_client = IdentityClient("us-east-1")

def handle_request(user_id: str, workload_name: str, request: dict) -> dict:
    workload_token = identity_client.get_workload_access_token(
        workload_name=workload_name,
        user_id=user_id,
    )
    return invoke_downstream_tool(request, auth_token=workload_token)
```

Prefer the `user_token` parameter (a JWT for the end user) over `user_id` when a JWT is available. AgentCore Identity validates the JWT's signature, issuer, and expiry; a plain `user_id` string is not verified by the platform.

Two practical implications for a platform built this way:

- **Downstream policy checks should evaluate the propagated user identity, not the calling agent's identity.** An AgentCore Policy rule scoped to `principal is AgentCore::OAuthUser` (the real AgentCore principal type) only works if the user's identity actually reached the Gateway making the tool call. See [policy authorization flow](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/policy-authorization-flow.html) for the full evaluation model.
- **Sub-agent-to-sub-agent calls need the same discipline as agent-to-tool calls.** If Agent A calls Agent B on a user's behalf, A needs to forward (or re-request) a workload access token scoped to that user rather than calling B with its own agent identity, or B has no way to enforce per-user authorization.

This pattern (propagate a user-scoped token through every hop, and enforce authorization independently at each hop rather than trusting the previous hop's decision) is the practical form of zero-trust for multi-agent systems: no single agent in the chain is implicitly trusted just because an earlier agent validated the request.

## Cost Governance with Application Inference Profiles

Token spend is a governance concern, not just a FinOps concern. An ungoverned agent with an uncapped model budget is the cost equivalent of an ungoverned agent with unrestricted tool access. Amazon Bedrock's **application inference profiles** are the primitive that makes per-agent, per-team cost attribution possible without building a custom metering layer.

An application inference profile is a Bedrock resource you create that wraps a foundation model (or a cross-region system-defined profile) and carries cost allocation tags. Callers pass the profile's ARN instead of a raw model ID; Bedrock attaches the profile's tags to the billing record for every request that flows through it.

```python
import boto3

client = boto3.client("bedrock-runtime")

response = client.converse(
    modelId="arn:aws:bedrock:us-east-1:123456789012:inference-profile/finance-agent-prod",
    messages=[{"role": "user", "content": [{"text": "Summarize this quarter's variance report"}]}],
)
```

A common tagging pattern for platform teams is a fixed five-tag schema applied to every application inference profile at creation time:

<div className="fancy-table">

| Tag             | Purpose                                                                          |
| --------------- | -------------------------------------------------------------------------------- |
| `ApplicationCI` | Links spend to a configuration item in the CMDB                                  |
| `Application`   | Human-readable application or agent name                                         |
| `Owner`         | Team or individual accountable for the spend                                     |
| `Environment`   | `dev` / `staging` / `prod` - separates experimentation cost from production cost |
| `ModelID`       | Underlying foundation model, for model-level cost comparison                     |

</div>

Tagged profiles flow into AWS Cost Explorer and Cost and Usage Report (CUR) 2.0 at a per-usage-type-per-day granularity. The profile-level tags alone only get you to daily aggregates, not per-call cost. For finer-grained, per-request token detail (for example, cost per individual conversation), pair application inference profiles with per-request metadata tagging on model invocation logs.

:::info
Only **application inference profiles** support cost allocation tags. System-defined (cross-region) inference profiles route requests across regions but cannot be tagged, so they are not sufficient on their own for cost attribution.
:::

A **Central AI Account** pattern extends this further for organizations running many agents: model access is centralized in one account, and every team's traffic flows through an application inference profile scoped to that team. This gives the platform team a single place to enforce model allowlists and budget alarms, while still attributing spend back to the originating team through tags.

### Additional cost attribution mechanisms

Bedrock's cost management capabilities are evolving rapidly. Beyond application inference profiles, consider these complementary mechanisms:

- **IAM principal-based cost attribution** — Bedrock now automatically attributes inference costs to the IAM principal (user, role, or federated identity) that made the call, without requiring profiles or tags. See [Introducing granular cost attribution for Amazon Bedrock](https://aws.amazon.com/blogs/machine-learning/introducing-granular-cost-attribution-for-amazon-bedrock/).
- **Bedrock Projects** — a higher-level construct for organizing AI workloads with built-in cost boundaries and team-scoped resource management. See [Manage AI costs with Amazon Bedrock Projects](https://aws.amazon.com/blogs/machine-learning/manage-ai-costs-with-amazon-bedrock-projects/).

These mechanisms complement rather than replace application inference profiles. Use profiles for tag-based attribution, IAM principal attribution for automatic per-caller tracking, and Projects for organizational scoping. See the [Bedrock cost management FAQ](https://docs.aws.amazon.com/bedrock/latest/userguide/cost-mgmt-faq.html) for guidance on combining them.

## Putting It Together

The governance architecture layers enforcement points across the request path: identity validation, Cedar policy evaluation, rate limiting, and guardrails each apply independently. Cedar enforcement is scoped to calls that pass through AgentCore Gateway; agents or services that call Runtime or backend systems directly do not pass through Gateway-based checks, so design tool access to route through Gateway where governance coverage is required.

:::info
The governance plane and enforcement plane work together as a **continuous loop**: policies are defined centrally, enforced at runtime, and observability data feeds back to refine policies and detect anomalies.
:::
