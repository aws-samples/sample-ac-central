# Multi-Tenancy & Reference Architecture

:::tip Who this is for
Architects designing multi-tenant agent deployments — isolation models, account topology, operating models, and the maturity path from experimentation to governed platform.
:::

Multi-tenancy is a cross-cutting concern that affects every layer of the agent platform. As multiple teams, business units, and use cases share the platform, proper isolation ensures security, performance predictability, and cost accountability.

---

## Multi-Tenancy Dimensions

Each platform layer requires its own isolation strategy. A "tenant" may be a team, business unit, application, or customer - depending on your organizational model.

<div className="fancy-table">

| Dimension | Isolation Requirement | Implementation |
|---|---|---|
| **Runtime & Compute** | Agents from different tenants cannot share execution contexts | Separate containers/micro-VMs, namespace isolation |
| **Tool Scope Boundaries** | Tenants access only their authorized tools and MCP servers | Per-tenant Gateway policies, Cedar authorization |
| **Data & Prompt Isolation** | One tenant's data never leaks into another's context | Tenant-scoped storage, prompt injection guardrails |
| **Memory Isolation** | Agent memory is partitioned per tenant | Tenant-prefixed memory stores, access policies |
| **Eval & Telemetry Separation** | Metrics, traces, and evals are attributed to the correct tenant | Tenant tags on all telemetry, separate dashboards |
| **Registry & Access** | Each tenant sees only their agents and approved shared agents | RBAC on registry, tenant-scoped discovery |

</div>

## Operating Models

How the platform team and domain teams interact determines the platform's operating model.

<div className="fancy-table">

| Model | Description | Best For |
|---|---|---|
| **Centralized** | Platform team builds and operates all agents. Domain teams submit requests. | Small organizations, early stages, regulated industries |
| **Decentralized** | Each team builds and operates independently. Minimal shared services. | Highly autonomous engineering cultures (high Shadow AI risk) |
| **Federated** ⭐ | Platform team provides shared services and guardrails. Domain teams build autonomously within boundaries. | Most enterprises - balances speed with governance |

</div>

:::tip Recommended
The **Federated** model is recommended for most enterprises. It provides the guardrails of centralized governance with the velocity of decentralized execution.
:::

## Organization Model

The federated model requires a dedicated Platform / Center of Excellence (CoE) team that enables domain teams.

### Platform / CoE Team

<div className="fancy-table">

| Role | Responsibility |
|---|---|
| **Platform PM** | Roadmap, prioritization, stakeholder alignment |
| **Platform Architect** | Reference architecture, standards, technology decisions |
| **Platform Engineers** | Build and maintain platform services, IaC constructs, self-service tooling |
| **Platform Ops** | Reliability, incident response, capacity management for shared services |
| **Platform Security** | Security standards, policy authoring, threat modeling, compliance |

</div>

### Domain Teams

Domain teams consume platform services and build agents for their business domain. They own:
- Agent logic and prompts
- Domain-specific tools and data
- Quality and evaluation criteria
- On-call for their agents

The platform team enables them with:
- Self-service onboarding
- Reusable templates and constructs
- Shared observability and governance
- Consultation and architecture reviews

## Platform Maturity Model

Organizations evolve through maturity levels. Each level builds on the previous one.

<div className="fancy-table">

| Level | Name | Characteristics |
|---|---|---|
| **L1** | Experimentation | Individual teams building PoCs. No shared infrastructure. Ad-hoc security. |
| **L2** | Foundation | Shared runtime and gateway deployed. Basic registry. Central observability. |
| **L3** | Scaling | Self-service onboarding. CI/CD with eval gates. Multi-team adoption. A/B testing via `agentcore run ab-test` (native Gateway-driven weighted splitting). |
| **L4** | Governed & Optimized | Full governance automation. Cost optimization. Continuous evals. Federated ops. |

</div>

:::note Native A/B testing vs infrastructure-level routing
AgentCore provides **native A/B testing** with Gateway-driven weighted traffic splitting. Use `agentcore run ab-test` (CLI) or the `CreateABTest` API to configure tests. Two modes are available:

- **Config-bundle mode** — tests prompt, tool, or model configuration variants on the same runtime ([docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/ab-testing-config-bundle.html))
- **Target-based mode** — routes traffic across different runtime endpoints ([docs](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/ab-testing-target-based.html))

For **infrastructure-level traffic splitting** across entirely separate deployment targets outside AgentCore (for example, a green-field re-architecture comparison), external mechanisms such as CloudFront, ALB weighted target groups, or Route 53 weighted routing remain an option. See the [A/B testing overview](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/ab-testing.html) for guidance on choosing the right mode.
:::

    <p><strong>Steps:</strong></p>
    <p>• Build self-service onboarding workflows<br/>
    • Implement CI/CD pipelines with evaluation gates<br/>
    • Add cost attribution and per-team budgets<br/>

    • Use infrastructure-level traffic splitting, such as CloudFront, ALB weighted target groups, or Route 53 weighted routing, only when you need network-layer distribution across deployment targets entirely outside AgentCore<br/>
    • Onboard 3+ domain teams to the platform</p>
    <span className="service-tag tag--gateway">Scaling</span>
  </div>

  <div className="tile-card">

    <p>• Automate governance with policy-as-code<br/>
    • Implement continuous online evaluations<br/>
    • Deploy multi-account architecture with SCPs<br/>
    • Establish federated operating model with CoE<br/>
    • Optimize cost with model routing and caching<br/>
    • Shadow AI detection and prevention workflows</p>
    <span className="service-tag tag--identity">Governed</span>
  </div>
</div>

:::info
You don't need to reach L4 on day one. Start with L1 (experimentation), validate the value, then invest in platform capabilities incrementally. Most organizations should target L2 within 3 months and L3 within 6-9 months.
:::
