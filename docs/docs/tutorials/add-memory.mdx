# Add Memory to Your Agent

## Why It Matters

Properly scoped memory transforms one-shot interactions into continuous relationships. Memory reduces repeated onboarding and lets an agent adapt to prior interactions, while its strategies can turn conversation events into recallable facts or summaries. It is a retrieval layer, not an authoritative database: store transactional, regulated, or audit-critical data in the system of record and give the agent only the context it needs.

## When to Use

| Condition | Recommendation | Rationale |
|-----------|---------------|-----------|
| Agent needs recall across sessions (returning users, prior context) | Add Memory | Users expect continuity; preferences and decisions carry forward across interactions |
| Single-turn Q&A only | Prefer session-only context | No persistence overhead; context is discarded after the response |
| Data must be authoritative (audit trails, regulated records) | Prefer system of record | Memory is a recall layer, not a source of truth; transactional data needs durability guarantees |
| Multi-tenant agent with verified identity | Add Memory | Stable actor IDs enable safe namespace isolation per tenant and user |
| Cannot establish tenant or user boundaries | Defer (resolve identity first) | Memory without isolation risks namespace contamination across users |

## What to Watch Out For

### Make tenant namespaces intentional

Memory isolation depends on the `actor_id` that your application supplies. Derive it from a verified identity claim and include the tenant boundary in the identifier design, such as a tenant-and-user pair. Never use a shared, caller-controlled, or unauthenticated actor ID: it can merge separate users' memory namespaces. Review [multi-tenancy guidance](/docs/agent-platform/multi-tenancy) alongside your identity design.

### Set PII retention boundaries before storing events

Decide which facts may be retained, for how long, and how users can request deletion before enabling long-term recall. Minimize or exclude raw PII, credentials, and regulated data; store the smallest useful fact rather than a full transcript. Keep audit records and contractual data in their authoritative systems, and disclose cross-session retention to users where appropriate.

### Bound retention with `eventExpiryDuration`

Set `eventExpiryDuration` to the shortest time-based retention period that satisfies the user experience. A short expiry is usually appropriate for temporary preferences or case context; use an explicit product policy before choosing longer retention. Test expiry and deletion behavior for each tenant, especially when changing a memory strategy or retention period.

## Common Mistakes

- **Treating memory as a database:** it improves recall but does not replace the durability, reporting, or audit guarantees of a system of record.
- **Using one actor ID for everyone:** this defeats tenant namespace isolation. Bind actor IDs to verified identities before invoking the runtime.
- **Keeping data indefinitely:** choose a time limit with `eventExpiryDuration` and include memory in deletion and privacy workflows.

For operational controls beyond these memory-specific decisions, use the [Production Readiness checklist](/docs/operate/production-readiness).

## What This Creates and What It Costs

Deploying this tutorial creates the following AWS resources:

| Resource | Notes |
|---|---|
| AgentCore Runtime | Hosts your agent code in MicroVM isolation |
| AgentCore Memory | Stores conversation facts and summaries with SEMANTIC and SUMMARIZATION strategies |
| ECR repository | Stores the packaged agent image |
| IAM execution role | Least-privilege role for the Runtime |
| CloudWatch log groups | Receives runtime, invocation, and memory extraction logs |

**Main cost drivers:**
- **Model inference tokens** — every invocation calls Claude Sonnet 4.5; memory extraction jobs also use model calls
- **Memory storage and retrieval** — AgentCore Memory charges for stored events and semantic retrieval calls
- **Runtime execution seconds** — billed per second of agent execution
- **Log ingestion** — CloudWatch charges per GB ingested and stored

**Scale-to-zero does not mean zero cost.** Memory records persist (until their `eventExpiryDuration` elapses), and ECR images and CloudWatch log retention continue to accrue charges even with no active traffic.

## Cleanup

When you are done with this tutorial, destroy the AWS resources it created:

```bash
# From your agent project directory
agentcore destroy
```

Verify resources are gone:

```bash
agentcore status
# Expected: no runtimes or memory resources listed
```

Some resources may persist after `agentcore destroy`:

- **AgentCore Memory records** — memory events are retained until `eventExpiryDuration` elapses; delete the memory resource explicitly if you need immediate removal
- **ECR repository** — may remain if images are still tagged; delete manually in the ECR console
- **CloudWatch log groups** — retained by default; delete manually to stop log storage charges

If `agentcore destroy` reports errors, see [Cleanup Failures](/docs/reference/troubleshooting#cleanup-failures).
